# pi-dashboard UI/UX 设计与改进

## 目标与边界

让用户更容易看懂信息、找到下一步并完成手头任务；美化不能损害正确性、可读性或现有操作。只改用户要求的页面和必要的共享组件，不顺手重做整站，不把功能问题伪装成视觉问题。

## 开始前

1. 先看根目录 `AGENTS.md` 和 `git status --short`。保留已有改动；不要覆盖、回退或清理与本任务无关的文件。
2. 沿着目标页面找到路由、页面组件、共用组件、数据/状态来源和相关测试。先理解页面怎么工作，再决定改哪里。
3. 查看现有设计基础：`frontend/src/index.css`、`frontend/src/themes/`、`frontend/src/components/ui.tsx`、`frontend/src/components/MaterialIcon.tsx`。确认当前页面使用的主题变量、字号、间距、图标和组件；不要只凭文件名假定组件行为。
4. 先写一份简短的页面设计说明：目标用户、要完成的任务、最关键的信息/操作、沿用的视觉语言、准备改变的部分和成功标准。内容清楚就直接推进并简短告诉用户计划；只有会改变方案的重要信息不清楚时才提问。
5. 如果能打开页面或截图，先看当前页面，并在改后用相同窗口大小复查；至少检查一个常用宽屏和一个窄屏。做不到就照实说明，不能把代码通过说成视觉验收通过。

## 设计判断

- 先按信息重要程度安排标题、内容、状态和主要操作；留白、对齐和密度要帮助用户扫描，不为了“高级感”牺牲信息量。
- 这是日常使用的控制台，不是营销落地页。每个边框、底色、图标、数字和动画都应帮助用户理解层级、状态或操作；删掉纯装饰元素。
- 视觉上可以有鲜明重点，但重点要来自当前页面的真实任务。避免无理由地把内容切成一排同样的圆角卡片、添加渐变/阴影/装饰标签，或照搬其他产品的风格。
- 优先使用项目已有的 CSS 变量和共享组件。主题样式位于 `frontend/src/themes/`，至少确认改动在相关的明暗/彩色主题下都可读；不要用硬编码颜色覆盖主题，也不要仅为一页改坏全局样式。
- 文案面向使用者：按钮写清会发生什么，名称前后一致；错误信息说明出了什么问题和用户能做什么；空状态给出有用的下一步。不要造假数据、假指标或无意义的占位文案。
- 明确检查加载、空、错误、成功、禁用等真实状态。信息不能只靠颜色区分；按钮、输入框和图标操作要有清楚的名字及键盘焦点。
- 保持窄屏可用：内容能收缩或换行，操作可触达，不出现无意的整页横向滚动。尊重已有断点和原生应用布局。
- 动效只用来解释用户操作或状态变化；避免页面载入时到处浮入、无意义的悬停动画，并保留减少动态效果的支持。
- 用长标题、长编号、连续无空格内容检查窄屏和 200% 浏览器缩放；允许安全换行或有解释的截断，不能盖住关键信息和操作。
- 页面有图表时，先确认它要回答的问题（趋势、比较、构成等），再选图形；标明单位、时间范围和必要的图例，保持数据含义与刻度真实，不为了好看改数据或误导比例。

## 实施方式

1. 动笔前先定一个小的视觉方向：指出最重要的信息、主要操作、布局变化和沿用的主题做法。先检查这个方案是否真的对应当前页面，而不是换一个常见模板。
2. 复用现有 React 组件、图标和样式工具。只改必要文件；不加新依赖，不复制一套组件，不改变 API、数据含义、权限或页面流程，除非用户明确要求。
3. 用现有主题令牌做颜色与状态；选择器尽量限制在目标页面，避免全局 CSS 副作用。状态颜色要符合项目现有语义。
4. 若预览可用，实际看改后页面并做一轮自查：层级是否一眼看懂、常用操作是否容易找到、文字是否可读、窄屏是否正常、是否有可删的装饰。按需要修正，不只凭代码猜效果。

## 验收与交接

- 按改动范围运行最有用的页面测试或前端检查；不要机械地跑无关全套测试。UI 代码改动时说明实际运行了什么、通过与否。
- 复查自己的差异，确认只包含本次需要的文件，已有用户改动仍在。没有截图/浏览器检查时，明确标注视觉效果未实测。
- 用中文简要报告：做了什么、检查了什么、还有什么没检查。不要把方案或代码已写好当作视觉验收完成。
- 遵守 `AGENTS.md`：不要自行运行 `./run.sh`、`./restart.sh` 或重启 dashboard 服务；若需要部署或重启，交由用户执行。
