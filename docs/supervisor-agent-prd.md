# Dashboard 工作监督台与事件流水账 PRD

- 状态：首版本地功能已实现；Jira/Lark 不作为本次交付范围，实际操作验收由用户执行。实现及自动验证证据见 [实施记录](~/repos/pi-dashboard/docs/supervisor-agent-implementation.md)。
- 技术设计：[工作监督台与事件流水账技术设计](~/repos/pi-dashboard/docs/supervisor-agent-tech-design.md)。
- 产品：Pi Dashboard。
- 本文用途：先共同理清用户场景、需要做的事情、范围与验收标准。
- 文档边界：PRD 说明“为什么做、做什么、用户如何使用”；工具、接口、数据结构、存储、组件、调度及集成方案留到后续技术设计（Tech Design）。

## 1. 主要需要做的事情

| 需求 | 要解决的问题 | 用户得到的结果 |
|---|---|---|
| 统一主 Agent 入口 | 不想在各页面重复输入和切换上下文 | 在同一个对话入口提问、记录进展、附截图、补录和更正 |
| 多 Session 工作监督 | 无法快速掌握多个会话正在做什么 | 看清当前进展、阻塞、下一步及信息是否过期 |
| 任务总结与人工待办 | 不知道哪些事情需要自己处理 | 获得任务摘要和明确的待决策、待提供信息、待验收事项 |
| 工作质量抽查 | 需要检查 Agent 的交付是否满足要求 | 根据验收标准查看发现的问题、证据和未检查范围 |
| 短期与长期任务追踪 | 日常行动与长期目标容易脱节 | 查看近期行动、阶段目标、依赖及长期无进展事项 |
| 事件流水账页面 | 跨角色协作过程散落在对话和截图里 | 按项目、Epic、Task 查看完整时间线及过程证据 |
| 复盘与卡点分析 | 不清楚项目慢在哪、如何优化 | 回顾关键步骤、等待、返工和交接，找到有证据的优化机会 |

以上是需求全景，不意味着全部同时进入首版；首版优先级在场景评审后确认。

## 2. 背景、用户与目标

### 背景

用户同时推进多个 Agent 会话和项目，还需要与 PM、后端等合作方协作。进度、回复、截图、中间结果和决策分散在不同地方，逐个翻找成本高，也不利于交接和复盘。

### 主要用户

- 同时管理多个 Agent Session（工作会话）的个人开发者或技术负责人。
- 发起项目并与 PM、后端等角色协作，需要持续跟进进展的人。
- 需要安排人工决策、抽查交付、追踪长期任务的负责人。

### 产品目标

让用户通过一个主 Agent 入口管理信息，在 Dashboard 中看清“现在怎么样、需要我做什么、过去发生了什么、哪里值得优化”。主 Agent 辅助整理和判断，不代替用户审批或凭空补全事实。

## 3. 主要使用场景

### 场景一：总览多个 Session 的工作状态

**情境**：用户同时运行多个会话，不想逐个打开对话。

**使用方式**：用户打开工作监督台，或问主 Agent“现在各个任务进展怎么样，有哪些卡住了？”

**预期结果**：看到各会话/任务的目标、当前进展、下一步、阻塞、最近更新时间和来源；分清已知状态、可能停滞与未知。能继续查看具体任务和相关证据。

### 场景二：汇总任务与人工需要做的事情

**情境**：Agent 或合作方正在等待用户提供信息、确认方案或验收，事项分散容易遗漏。

**使用方式**：用户问“今天有哪些需要我处理的事情？”并在同一入口记录处理结果。

**预期结果**：获得事项、等待原因、建议行动、关联任务和来源；已处理事项与仍在等待的事项清晰区分。用户可纠正、忽略误报或补充负责人。

### 场景三：抽查交付质量

**情境**：某任务报告完成，用户希望检查实际交付是否符合要求。

**使用方式**：用户指定任务、验收标准及允许检查的交付物，让主 Agent 抽查。

**预期结果**：得到“本次抽查未发现问题 / 需关注 / 信息不足”的结论，以及逐项证据、问题影响、建议行动和未检查范围。抽查意见不等于正式验收，不声称执行过未实际执行的验证。

### 场景四：持续记录与 PM、后端的协作过程

**情境**：用户发起一个项目，经历需求确认、开发、联调、阻塞、修复和验收，希望保留自己及合作方的状态、回复与中间结果。

**使用方式**：在唯一的主 Agent 入口持续描述更新，并附截图或文档。例如：

1. “记录这个项目的发起目标和参与者。”
2. “PM 已确认需求范围，这是回复截图。”
3. “给 XX Task 记一条：后端正在开发接口，预计明天完成。”
4. “联调发现字段不一致，正在等后端修复，这是问题截图。”
5. “后端已修复，联调通过，附验证结果。”

**预期结果**：每一步形成可追溯事件，记录谁在做什么、何时发生、结果、下一步及证据。用户明确要求记录且信息充分时直接保存并返回记录摘要与链接；无法确定归属或关键内容时才询问，不冒充合作方确认。

### 场景五：补录和更正历史

**情境**：用户今天才记录昨天的回复，或发现之前记错了时间、参与者或内容。

**使用方式**：在同一入口说“补录昨天后端的回复”或“把刚才那条发生时间改成昨天”。

**预期结果**：发生时间与录入时间明确区分；更正可追溯，不用最新摘要覆盖历史事实。定位不唯一时先确认。新增历史事件不自动改变当前任务状态。

### 场景六：浏览事件流水账并做复盘

**情境**：用户希望了解某个任务或整个项目的发展历史，用于交接、复盘或分析。

**使用方式**：在 Dashboard 的“事件流水账”页面选择项目、Epic（任务集合）或 Task（具体任务），按时间、参与者、阶段和事件类型查看；通过主 Agent 请求复盘总结。

**预期结果**：Task 展示自身历史，Epic/项目汇总相关任务，不重复呈现同一事件。用户能打开回复与截图，查看关键决策、中间结果、阻塞与恢复，并从复盘结论回到原始记录。页面用于查看、筛选和分析，不另设输入窗口。

### 场景七：分析项目主要卡点

**情境**：项目推进较慢，用户想知道具体慢在哪个环节，为后续优化提供依据。

**使用方式**：用户问“这个项目主要卡在哪里？哪个阶段等待时间最长？哪些问题反复出现？”

**预期结果**：基于记录指出阶段历时、等待处理、交接延迟及返工，附对应事件和分析范围。区分推进历时、等待时间与实际工时；缺少起止记录时显示信息不足，不凭消息间隔评价个人效率，不自动归责。

### 场景八：追踪短期行动与长期目标

**情境**：项目跨周甚至跨月推进，用户需要兼顾近期安排与长期方向。

**使用方式**：用户询问近期要推进什么、长期目标有什么变化、哪些依赖未解决。

**预期结果**：看清目标、阶段、关联任务、里程碑、下一步、依赖和最近有效进展。只有明确截止时间和可靠记录时才判断逾期；长期无更新提醒须说明依据。

## 4. 已确认的产品规则

### 4.1 唯一输入入口

- 人工输入统一通过主 Agent 对话，包括提问、进展、回复、截图、补录、更正及相关确认。
- 各页面负责展示、筛选、查看附件和分析，不增加独立聊天框或录入窗口；可以引导用户回到主入口处理当前事项。
- 普通明确记录不重复确认；主 Agent 主动建议的记录或未确认的截图解读先供用户确认。
- 成功保存后返回记录对象、内容摘要和链接；失败明确说明，不报虚假成功，重试不能产生重复记录。

### 4.2 过程记录内容

应能回答：属于哪个项目/Epic/Task、发生了什么、何时发生、谁参与、谁记录、信息来自哪里、有什么结果或证据、下一步是什么。

保留原始回复/摘录、用户描述与 Agent 归纳的区别。支持截图、文档和中间结果；未知信息不强行补全。外部合作方可以由用户代录，不要求对方接入系统。

### 4.3 当前状态与历史分开

新增事件不等于更新当前任务状态。状态变更由用户明确发起并确认，保留变化过程；历史更正可追溯。覆盖修改、删除和对外同步需要额外确认，明确指定记录及字段的普通更正不反复确认。

### 4.4 时间与分析口径

- 区分事件发生时间、录入时间和修订时间。
- 阶段历时与等待时间需有可确认的起止节点；未结束的区间说明“截至当前”。
- 实际工时只能来自明确填报或可靠计时，不能用在线时间、回复间隔代替。
- 并行任务历时不能简单相加成为项目历时，投入不能重复计入。
- 分析与复盘必须说明覆盖范围和缺失信息；结论有来源，不以单一分数替代证据。

### 4.5 信息、权限与隐私边界

- 只观察用户已授权、实际可访问的会话和任务；外部协作方的转述不视为自动获取的实时状态。
- 数据离线、过期、冲突、来源缺失或附件不可用时明确提示，不静默猜测。
- 不默认读取所有完整对话；用户可排除敏感会话和内容。
- 截图可能包含同事信息、聊天内容或凭证，需提示遮挡并确认有权记录；不默认公开分享，对外复盘由用户确认范围。
- 保留周期、删除要求与可见范围须在产品评审中明确，不强制永久保留敏感原文。
- 不自动审批、关闭任务、发布或接管其他会话；抽查不取代既有测试和发布门禁。

## 5. 首版范围

### 建议纳入

- 唯一主 Agent 入口，以及可用范围内的多会话/任务总览。
- 按需任务摘要、人工待办和用户指定交付的质量抽查。
- 项目/Epic/Task 事件流水账，包含回复、截图、补录和更正。
- 基于已有记录的基础时间展示、卡点分析和按需复盘。
- 基础近期行动与长期目标追踪，以及有明确依据的停滞/逾期提示。

### 后续再评估

- 定时摘要、主动通知与更丰富的长期目标视图。
- 跨项目趋势和相似项目对比。
- 更多外部会话来源、多人共同录入及外部任务系统自动同步。
- 更多复盘导出形式。

### 首版不承诺

自动读取外部聊天、自动截屏、自动分配/干预工作、自动验收/关闭/发布、绩效评分或自动归责。Jira/Lark 自动同步不作为首版前提，不可用时应明确标记且不影响本地使用。

## 6. 验收与效果观察

### 场景验收

1. 多会话总览能区分当前信息、过期信息和未知状态；摘要及人工待办有来源。
2. 用户在同一入口提交明确进展及截图后获得成功回执，能在对应 Task 时间线查看；归属不明确时先询问，失败不报成功。
3. “发起 → PM 确认 → 后端开发 → 联调阻塞 → 修复验证”能完整回顾，包括本人记录、合作方转述和中间结果。
4. 补录按真实发生时间呈现，更正可追溯；新增事件不擅自改变当前状态。
5. Task、Epic、项目都能查看相关时间线，回复和截图可打开；各页面没有独立输入窗口。
6. 复盘及卡点结论可追溯到事件；缺少节点不编造耗时，阶段历时不冒充实际工时。
7. 质量抽查说明验收项、发现与缺口；缺乏证据时报告信息不足，未检查范围明确。
8. 敏感内容与无权限信息不被扩大使用；没有未经确认的状态变更或外部动作。

### 成功指标（目标值待评审）

- 用户了解全局进展、找到待办和找到指定历史事件所需时间。
- 记录一条进展到成功回执的用时，以及重要事件的记录完整性。
- 摘要、抽查和复盘结论的可追溯比例，以及用户纠错/误报比例。
- 人工待办从提出到处理的时长。
- 卡点分析经用户核实成立并用于流程改进的情况。
- 未经确认的状态变更/外部动作、过期信息冒充实时、历时冒充工时的次数，目标均为 0。

## 7. 下一轮需要理清的问题

1. 哪几个场景最重要？首版是否以“协作记录 → 时间线 → 复盘”为优先闭环？
2. 自动观察首期只覆盖当前 Dashboard 会话，还是需要其他机器/Agent？
3. 首期由用户代录合作方进展，还是需要 PM/后端直接参与？
4. 哪些内容允许用于总结与抽查？是否需要每次指定范围？
5. 近期与长期任务首先需要展示到什么程度？
6. 首期只需阶段历时和等待时间，还是也需要实际工时填报？
7. 摘要和提醒先按需还是定时？通知渠道有哪些需求？
8. 记录、截图和复盘的可见范围、保留周期与删除需求是什么？
9. 首期验收样例、试用周期和成功指标目标值如何确定？
