# Pi 子助手实际运行与 token 成本审查

状态：只读分析；未修改运行器、模型配置、权限或服务。
关联方案：`pi-dashboard/docs/subagent-workflow-lifecycle-tech-design.md`。
用户方向：主助手用较强模型负责策略、验收与升级判断；执行子助手使用较便宜模型。明确不采用 Agent Teams。

## 1. 结论

当前实现支持进程隔离和显式模型选择，但默认行为没有落实“便宜模型执行”：不填 model/thinking 会继承主助手。fresh 子助手不复制父对话，却仍加载较重的全局/项目指令、扩展、技能和工具说明。

实际可读样本显示：7 个历史子助手中 4 个使用 `azure-gateway/gpt-6.1-sol`，3 个使用 `openai-codex/gpt-5.6-luna`。系统说明中位数 33,525 字符，工具定义中位数 43,077 字符、47 个工具，任务提示中位数仅 909 字符。只换模型能改变单价，不能解决上下文、反复读取、输出和主助手回收成本。

建议优先级：显式默认执行模型 → 最小任务包与角色工具面 → 有界工具返回/结果交接 → 有依据的升级与成本验收 → 单次任务资源收尾。

## 2. 样本与统计口径

### 范围

- trace 根目录：`~/.pi/agent/pi-traces/sessions`。
- 第一批快照统计开始：2026-10-15 11:03:03 UTC。
- 当时共 1,602 个目录，按 UUID 文件名排序取最近 100 个；这不是全历史审计，也不保证文件修改时间排序。
- 读取 61 个事件文件，共约 386 MB；25 个目录无权限，14 个文件因大小/总读取预算未纳入。
- 排除本次主会话及新开的只读审查子助手，避免用本次审查证明历史行为。
- 历史样本：52 个根会话文件记录、7 个子助手文件记录；部分根会话只有启动/退出事件，没有模型用量。
- 此样本不足以覆盖多阶段工作流，不能据此给工作流规模下成本或失败率下结论。

### 去重与计费

- 按 eventId 去重；用 `message_end` 的 assistant usage 累加，不重复统计 turn_end、agent_end 中复制的同一消息。
- 输入侧累计 = input + cacheRead + cacheWrite，表示历次模型读取的累计量，不是独立文本量或全部按普通输入价格计费。
- reasoning 单列，不再次叠加到 output/total，避免重复计费。
- 使用 trace 的 reported cost，只是配置计算的估算，不是供应商账单。不同渠道、缓存计价和配置可能不同。
- 文件大小、工具返回字符数、系统提示字符数不直接换算成 token。工具事件也不必然一一等于独立模型请求，run_code 可以包含多个工具调用。
- 完整父会话常是被大小限制排除的文件；第一批只有本次审查构成完整父子配对。因此不报告历史“同父模型比例”，只报告子助手实际使用模型。

## 3. 运行机制与有证据的缺陷

### 3.1 默认模型选择与目标不一致（最高优先）

`subagent_start` 使用 `params.model || currentModel(ctx)`、`params.thinking ?? currentThinking(ctx)`。工作流请求也携带主会话模型，任务未覆盖时继续继承。

证据：

- `pi-tsien-extension/packages/pi-tsien-subagent-workbench/src/index.ts:1099-1106`
- 同文件 `:780-797`
- `pi-tsien-extension/packages/pi-tsien-subagent-workbench/src/providers/pi-rpc-process-provider.ts:712-713`

这是确定的默认策略问题。历史 4 个强模型任务不必然全部属于误用；需结合任务难度与授权判断。也不能从模型名称直接判断准确价格。

### 3.2 fresh 只隔离对话，不提供轻量角色环境（最高优先）

provider 创建新 RPC 进程，不 fork 父对话。默认开启工具、扩展、技能、提示模板、context files；cwd 决定项目上下文读取范围。实际 trace 的 33,525 字符系统说明与 47 个工具确认启动包较重。

证据：`pi-tsien-extension/packages/pi-tsien-subagent-workbench/src/providers/pi-rpc-process-provider.ts:635-640,825-852`。

不要把“0 轮父历史”误认为“0 全局规则”。完整安全与权限规则不能为省 token 被关闭；可以去掉执行角色用不到的目录说明、技能清单和协调工具。

部分子助手实际调用了 memory_update/memory_search 等与纯执行不一定有关的工具。它说明执行角色工具面较宽，不单凭调用名称认定违规；需核实原任务授权。子助手完成回答也可能混入继承的全局回复规范，与结构化结果约定相冲突。

### 3.3 工具返回与重复读取增加执行成本（高优先）

工具返回最大 110,659 字符；只读子助手有 39 条 assistant 消息、92 次 read，返回最大 51,654 字符。大量文本会累积进入后续模型输入，命中缓存也仍有费用和延迟。

后续针对三个子助手的较晚快照，已观察到两项分别有 124 次 read/40 次相同路径与范围重读、65 次 read/9 次同范围重读。它们也存在编辑动作，重读可能是修改后的验证，不能把这些次数全部算成浪费。这是检查无变化重读、错误重试、过滤导致补读的候选信号。

优化应先定位符号、读取必要范围、保存证据引用；不要让便宜模型每次从仓库首页开始扫。错误必须暴露并修复原因，不用吞错、无声降级或无限重试换取省钱表象。

### 3.4 工作流交接有安全硬限，但缺少实用成本预算（中优先）

工作流每个输入摘要最多 8 KiB，artifact 描述单个最多 512 字节，多输入会一起拼接。底层 service 的默认 task/context/output 上限分别为 1/8/8 MiB，并进行校验。

证据：

- `pi-tsien-extension/packages/pi-tsien-subagent-workbench/src/workbench-controller.ts:438-506`
- `pi-tsien-extension/packages/pi-tsien-subagent-workbench/src/subagent-service.ts:18-20,728-749`

所以不是“没有总限制”，而是这些限制用于防止异常大载荷，远大于正常委派预算。应增加整次交接的 token/文本成本预算，避免大量兄弟结果累计、同一结论在多阶段反复传递。

### 3.5 结果通知要区分提醒、取回和续跑（中优先）

成功完成通知通常采用 nextTurn，不主动触发主助手新轮次；失败且主助手闲置时才 followUp。结果收集会从任务登记处取回输出。该设计避免每个成功任务立即唤醒昂贵主助手，但可能让等待成功结果的任务停在闲置状态。

证据：`pi-tsien-extension/packages/pi-tsien-subagent-workbench/src/index.ts:982-1007,1536-1575`。

这不是已证实的重复计费错误。应根据依赖状态决定：无关成功项只做简短提醒；下一步依赖这些结果时合并唤醒并只取回一次必要内容。大结果存为 artifact，主助手接收摘要和引用，不重复读全量记录。

### 3.6 单次直接任务与会话复用没有明确产品区分（生命周期优先）

provider 用 Map 保留 session/子进程，一轮结束清除 activeRun，但不立即 stop；工作流终态有专门 session 关闭路径。直接任务则保留以支持继续使用或容量回收。

证据：

- `pi-tsien-extension/packages/pi-tsien-subagent-workbench/src/providers/pi-rpc-process-provider.ts:715-753`
- `pi-tsien-extension/packages/pi-tsien-subagent-workbench/src/workbench-controller.ts:1935-1958`

这是“临时执行”与“可继续会话”语义不清，不应直接定性为无界内存泄漏。也不能假定闲置进程会持续花 token；主要直接影响进程、内存与 Dashboard 列表。一次性任务在结果可靠交接且无活动工具/后台命令后释放；后续追问用已支持的恢复路径。

## 4. 推荐的成本策略

### 主助手

负责澄清目标、确定范围、划分任务、预算、关键设计、授权和最终验收。读取简短证据与产出，不重复完成子助手已经完成的全量扫描。昂贵模型不必在每轮都使用最高思考等级；高思考留给真正的策略与难题。

### 执行选择

| 工作 | 默认路径 | 升级条件 |
| --- | --- | --- |
| 计数、格式转换、固定字段提取 | 现有程序/固定工具，能不用模型就不用 | 输入确有歧义才调用模型 |
| 已定位的小任务、只读检查 | 显式较便宜模型，low/medium 按难度选 | 一次明确失败或证据不足，交回主助手判断 |
| 有清楚边界的实现、多文件调查 | 经基线验证的执行模型，必要时 medium | 验收失败、设计冲突或任务超出边界 |
| 授权、最终架构、高风险取舍 | 主助手 | 不因省钱下放 |

可先用已验证可调用的 `azure-gateway/gpt-5.6-luna` 做候选执行模型；本次独立源码审查使用此模型，但主助手纠正了“交接没有总上限”的不准确表述。这说明应验收便宜模型，而不是无条件相信输出。其他 flash 模型先做同题基线，不从名字断言更便宜或更准确。

未填模型不应默认继承昂贵主模型；显式要求使用强模型时保留覆盖能力并记录升级原因。现有 provider 不允许同一 session 改模型或 thinking（`pi-rpc-process-provider.ts:725-733`），升级需要新执行会话及简短交接，不能给旧会话发一个新模型参数假装升级。修改默认策略是后续实现内容，本次没有改配置。

### 最小任务包

只传目标、允许路径/关键入口、约束、验收、结果格式；不传父历史、文件正文、原始日志或兄弟完整输出。主助手先提供准确入口，子助手不再重复全仓库发现过程。

现有 1,500-token 任务包约定可作为上限，不是每次要填满。普通任务尽量更短；整体输入预算必须包括系统说明与工具定义，而不只检查 task/context。

### 角色环境

按只读检查、代码执行、资料检索选择必要工具与技能。保留安全护栏、权限校验、trace 与必要结果交接；不要简单 `--no-extensions`。最小工具面应来自真实支持的运行器/权限协议，不仅靠提示说“不要调用”。

### 结果与预算

采用短摘要、最多五条证据、artifact 路径、风险和未完成项；大型产物外置。不强制所有结果同一个短长度而遗漏关键失败。结构化格式应有验证，不把软约定当强制协议。

为每类任务设独立轮次、输出、累计费用与时长预算。到软预算时停下汇报阻碍，由主助手升级或调整范围；不每次预算到达就把整个记录交给昂贵模型重做。

## 5. 如何验证节约是真实的

净成本包括：主助手策略 + 子助手启动说明 + 执行输入输出 + 主助手回收/复核 + 失败重做。不能只比较子助手单价，不能用删除证据或降低验收标准制造省钱。

用同一组代表性任务比较，每次只改一个主要因素：

1. 基线：当前默认模型与上下文。
2. 实验 A：只改变执行模型，保持提示、工具与验收一致。
3. 实验 B：保持已选执行模型，只缩小角色工具/上下文。
4. 实验 C：改善结果交接和有界读取，观察主助手回收成本。

记录：任务/模型/数据版本、命令或 task id、首次验收通过率、重做次数、主助手复核 token、输入/cacheRead/cacheWrite/output、估算净成本、完成时长和关键失败。按任务种类分别看，不混成一个漂亮均值。

本次没有运行模型对照实验，没有证明具体节省百分比。推荐先解决确定的继承默认与启动包问题，再用验收数据决定全面切换。

## 6. 与展示方案衔接

原方案的完成项收起、父子导航、工作流分层仍成立。补充两个依赖：

- 展示成本应同时显示执行模型、思考等级、任务预算与结果是否已交接，不能把“收起”作为省 token 的证据。
- 资源释放改动放在运行器权威源码，Dashboard 不在前端自动调用结束进程接口。

实施顺序可以先做低风险行为规范与展示；运行器默认模型/角色环境需要单独评审与回归，不能顺带改变全部会话加载行为。

## 7. 已完成与尚未验证

已完成：有界 trace 统计、排除审查本身、运行器静态检查、一次便宜模型独立审查、主助手复核及纠正、保留脱敏元数据和结论。

尚未验证：不可读和过大文件的全量覆盖、全部父子模型配对、真实供应商账单、所有重读是否必要、模型切换后的质量、实际进程回收与恢复竞争、工作流大规模运行成本。

未实施：模型默认切换、权限裁剪、上下文/预算硬约束、通知策略、运行器退出、部署或重启。以上均为后续候选，不是已完成改动。
