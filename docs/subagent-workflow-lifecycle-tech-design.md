# 子助手与工作流展示、成本与收尾改进 — Tech Design

状态：设计草案；已合并 trace 统计和运行器只读审查，未实施或完成运行验证。
范围：pi-dashboard 与子助手运行器的必要改动；保留现有编排、权限与同步机制。

## 1. 目标与结论

子助手完成后不再挤满页面，但结果仍可查看，失败和等待批准不被隐藏。工作流按层级组织，不把所有子助手当成同级主会话。临时子助手在完成交接后释放执行资源，展示和资源管理各自负责。

同时落实模型分工：主助手用较强模型负责策略、授权和最终验收；边界明确的执行任务使用经过验证的较便宜模型，机械工作优先用程序。省钱看整个任务的净成本，不能只比较子助手单价。

执行分为五阶段：完成项与父子导航 → 工作流层级 → 执行模型选择 → 上下文、交接与预算 → 运行器收尾。展示与模型基线可以独立推进；成本实验每次只改一个主要因素，不能同时切模型、删工具、改提示。复用现有组件、快照、事件通道和执行能力，不重写编排系统。

不采用 Claude Code Agent Teams：它仍是实验性功能，已被用户明确排除。仅借鉴普通子助手、工作流与 OpenCode 的父子会话组织。

### 2.1 运行器事实与 trace 基线

详细证据：`pi-dashboard/docs/research/subagent-trace-token-audit.md`。以下区分源码事实、样本观察与目标设计。

| 项目 | 已确认事实 | 设计响应 |
| --- | --- | --- |
| 默认模型与思考等级 | 未填参数时继承主助手；工作流任务也可能继承 | 增加执行角色的默认选择，不靠每次提示提醒；强模型覆盖须明确 |
| fresh 上下文 | 新进程/新对话，不复制父历史；仍默认加载工具、扩展、技能、提示模板和 context files | 隔离父历史之外，再按角色缩小启动包，保留安全与追踪 |
| 同会话升级 | provider 不允许同一 session 改模型或 thinking | 升级新建执行尝试，用短交接保留原证据，不覆盖旧尝试 |
| 工作流交接 | 单摘要上限 8 KiB；底层 task/context/output 上限为 1/8/8 MiB | 已有异常载荷防护，但需另加正常任务的整体成本预算，不宣称没有硬限 |
| 完成通知 | 成功通常 nextTurn；失败且主助手闲置时 followUp | 依赖结果时合并推进，无关完成只提醒；重复或延迟通知不重复取全文 |
| 执行收尾 | 直接任务结束后保留会话；工作流终态有专门关闭路径 | 区分一次性执行与继续会话，不把保留行为直接定性为内存泄漏 |

第一批统计按 UUID 文件名取最近 100 个目录，读取 61 个事件文件；25 个目录无权限、14 个文件因大小预算未纳入。排除本次主会话与审查子助手后，有 7 个历史子助手样本：4 个 `azure-gateway/gpt-6.1-sol`，3 个 `openai-codex/gpt-5.6-luna`。不能据此断言所有强模型任务都是误用。

系统说明中位数 33,525 字符、工具定义中位数 43,077 字符/47 个工具，而任务提示中位数仅 909 字符；工具返回第 90 百分位 17,646 字符，最大 110,659 字符。追加三个样本的首次响应输入侧约 18,569～19,680 token；追加父会话扫描超时，未完成全部模型配对。

统计按 eventId 去重，仅累加 assistant 的 message_end 用量；缓存读取/写入与普通输入分开，reasoning 不再重复叠加到输出。字符、日志文件大小不是 token；reported cost 是配置估算，不是实际账单。当前没有对照实验，不承诺具体节省比例。

## 3. 范围与非目标

### 范围

1. 普通子助手的活跃、需处理、已完成、已停止分组。
2. 主会话 → 工作流 → 阶段 → 子助手的导航与统一计数。
3. 完成后保持结果入口与当前详情，不自动删除历史。
4. 临时子助手结果交接、执行退出与重复通知的收尾设计。
5. 两种 Dashboard 数据入口的兼容，以及可观察的验收证据。
6. 主助手策略/子助手执行的模型默认选择、明确升级与角色工具面。
7. 最小任务包、有界读取和工作流交接、重复通知收敛与净成本验收。

### 非目标

- Agent Teams、长期队友、队友直接通信或共享团队任务池。
- 改造 Pi 核心、新增任意脚本执行器、重做通用模型路由或 GPU/集群资源调度；仅增加执行角色必要的模型选择和任务成本预算。
- 为所有历史助手新增永久数据库、跨宿主重启恢复所有易失状态。
- 自动删除记录、按闲置时间杀进程、由浏览器扫描或管理任意系统进程。
- 借此重做整站样式、修改无关会话排序或启动部署服务。

## 4. 用户任务与页面设计

用户需要快速知道：谁还在工作，哪里需要自己处理，完成结果在哪里，工作流走到哪一步。执行详情另显示实际模型、思考等级、升级原因、用量/预算状态及交接状态；只显示来源已提供的字段，不猜价格或把计划模型冒充实际模型。

沿用现有主题变量、文字加状态图标、侧栏与详情抽屉。状态不能只靠颜色；长标题可截断但可查看全文，窄屏不出现整页横向滚动。

```text
主会话
  ├─ 活跃工作
  │   ├─ 普通子助手：查找相关代码 · 运行中
  │   └─ 工作流：代码检查 · 已完成 12/20 · 失败 1
  │       ├─ 阶段一
  │       │   ├─ 子任务甲
  │       │   └─ 子任务乙
  │       └─ 阶段二
  ├─ 需要处理：失败 / 等待批准 / 状态无法确认
  ├─ 已完成（默认折叠）
  └─ 已停止（默认折叠）
```

- 成功状态确认后立即从活跃列表移出；不照搬其他产品的 30 秒记录消失策略。
- 归档在本文仅表示展示分组，不表示写入永久存储或删除数据。
- 失败项保留清晰入口和失败摘要，不能因超时自动隐藏。
- 已停止项不算成功；主动停止后移入独立分组。
- 等待批准仍可见，只在来源明确上报时显示该状态。
- 详情选中用稳定任务标识，不因列表过滤或会话退出切换到别的助手。
- 工作流内部助手只在对应阶段展示，不重复占普通助手列表顶层入口。
- 数据缺失的助手仍显示“状态待确认”，不推断成功、不丢弃。
- 主侧栏以主会话为一级入口；无可见父会话的子助手放入“未关联子助手”入口，不能直接隐藏。

## 5. 状态与关联模型

### 5.1 三个独立维度

| 维度 | 权威来源 | 规则 |
| --- | --- | --- |
| 任务状态 | 工作台/工作流运行器的任务记录 | 决定活跃、完成、失败等分组 |
| 执行与连接状态 | 运行器进程事件、Live Session 注册表 | 连接丢失不等于执行退出，idle 不等于任务完成 |
| 展示状态 | 前端当前页面 | 决定分组展开、详情选中；无权改变任务或杀进程 |

第一阶段先做纯展示投影，不修改 `LiveSessionStatus` 的含义。

投影层统一现有来源的明确状态，例如 completed/succeeded/done → 已完成，failed/error → 失败，cancelled/interrupted → 已停止。queued、paused、blocked 等只有在确认来源语义后映射；未知值保留原值并显示待确认，不做“默认成功”。最终映射表以运行器实际契约为准。

连接维度第一阶段只展示已连接、重连中、当前无连接。后续只有收到权威退出证据才标为“执行已退出”；不能仅凭注册表移除得出这个结论。

### 5.2 稳定身份

- 所有记录以父会话或 slot 限定作用域，防止跨会话串数据。
- 任务/会话/工作流/阶段标识分别保存，不把工作流 id 当成单个助手 id。
- `processInstanceId` 仅标识一次进程实例，不作为历史任务的主键；PID 可能复用。
- 优先使用来源提供的显式 task/session/workflow 关联；现有 `subagentWorkId` 前缀约定只能作为已核实的兼容路径。
- 关联不明确时显示未关联项，不凭标题、模型或相邻时间猜关系。
- 一个工作流任务重试时，要区分旧执行与新执行；旧尝试不覆盖，父级任务只计一次。

### 5.3 快照与事件

复用已有 revision 和事件序号，重连后以最新权威快照恢复，不以浏览器定时器推断终态。

已完成列表的数据来自任务记录，不来自活跃注册表。进程退出后，任务摘要、结果、错误仍可从原记录或已存在的会话历史读取。第一阶段核实当前实际保留范围；结果来源不可访问时明确显示不可用，不展示假内容。

不默认把所有日志拷贝进一个新缓存。若任务快照不能支持退出后的结果查看，先复用已有历史读取；仍不足时，补最小结果引用并在实现评审中确定保留边界。

## 6. 架构与职责

```text
子助手/工作流运行器（拥有任务、结果、进程与通知）
  → 已有扩展桥或 Live Session feature 快照
  → 小型状态与关联投影
  → 主会话活跃区 / 工作台 / 工作流阶段详情

执行命令：页面 → 已有鉴权与受限命令通道 → 运行器
```

### Dashboard

- 复用现有两种入口，不把 `subagent-workbench` 与 `subagent-workflow` 当作同名协议直接互换。
- 共享最小的状态、分组、计数与关联函数；不复制一套工作流渲染器。
- 第一阶段不增加后端执行命令、不扩大权限。
- “收起记录”“停止任务”“关闭执行会话”明确区分按钮含义。

### 运行器（模型、成本与收尾阶段）

- 负责执行模型选择、角色权限与启动上下文、任务成本预算，以及结果形成、交接记录、执行资源释放与退出证据。
- Dashboard 读取实际模型和用量；浏览器不自行更改模型、删除安全工具或推断模型账单。
- 负责恢复/追问能力，Dashboard 不保证已退出进程仍可直接收消息。
- 在其权威源码与支持的同步/安装流程内修改，不补丁式修改已安装副本。
- 初稿未读取运行器实现；后续只读审查确认普通任务保留会话、工作流终态存在关闭路径。证据与成本分析见 `pi-dashboard/docs/research/subagent-trace-token-audit.md`。下面仍是目标收尾协议，不表示改动已实施或运行验证已通过。

## 7. 完成收尾与资源释放

目标顺序：

1. 保存最终结果或明确失败原因，形成可访问记录。
2. 记录该次执行的终态，并可靠安排结果交接。
3. 确认交接已进入可恢复的队列或已被接收；仅发送但无法确认时不能宣称交接完成。
4. 确认当前没有后续轮次、执行中工具或仍由该执行负责的后台命令。
5. 由运行器释放本次执行资源，并记录退出结果。

展示分组可以在确认任务成功时更新，但“结果已交回”“资源已释放”必须分别有证据。不能用页面是否仍显示判断清理是否完成。

- 后台命令仍在运行时，先核实归属与通知接收者；不得静默丢弃、错误取消或提前结束唯一接收进程。
- 追问与清理并发时由运行器串行决定：接受追问则开启新轮次；资源已释放则使用已支持的恢复/重新启动路径。未支持时禁用按钮并说明，不吞掉消息。
- 不等待用户看过结果才退出；人是否查看结果不是资源释放条件。
- 若交接失败或退出失败，显示具体问题，不把它包装成已全部完成。
- 现有“关闭子会话”属于显式中止/结束动作，不能在收到成功状态时由前端自动调用。

重复通知按“父作用域 + 任务标识 + 执行尝试标识”区分。重复传输不追加第二条完成记录，也不触发第二次主助手自动轮次。重试产生新尝试，应允许新的完成通知。若需要跨重连或宿主重启保证，应由拥有通知队列的层保存状态，不能只靠组件本地集合。

后台完成事件、定时跟进和子助手结果提醒可能在主助手已经处理后才到达。本次分析也出现了这种延迟送达；它是需要收敛的行为，不据此断言底层重复计费。统一已处理标识；到达后先核对状态，已交接/已验收则不再次收集全文或启动分析。存在可靠完成事件时，不给同一任务叠加多个定时检查；兜底检查完成后取消，已排队的旧提醒也必须幂等消费。

成功项不一律唤醒主助手。下一步依赖结果时登记依赖，满足后合并推进；无依赖的成功结果只保留简短提醒。失败、等待批准和实际阻碍仍及时呈现，不能为省钱隐藏。

## 8. 工作流计数与控制

- 顶层计数是普通任务或工作流数量，不是工作流中的进程总数；需处理项单独计数。
- 工作流进度按逻辑任务计数，完成、失败、停止分别统计；不可用阶段数伪装成任务数。
- 跳过任务单独显示；任务总数为零时显示“尚无任务信息”，不显示误导性的完成百分比。
- 优先展开当前阶段和有错误的阶段，完成阶段默认折叠。
- 选中任务可在执行退出后查看记录；可用时另提供实时会话入口。
- 暂停、恢复、失败任务重试仅在确认运行器能力、补齐桥协议与命令白名单后开放。现有工具侧能力不等于网页接口已经支持。
- 不为展示改动扩大执行权限；主会话与不同 slot 的记录和命令必须隔离。

## 9. 模型分工与 token 成本设计

### 9.1 分工与默认选择

| 工作 | 默认承担者 | 边界 |
| --- | --- | --- |
| 目标、拆分、关键策略、授权、最终验收 | 较强模型主助手 | 读取必要证据，不重复执行完整调查 |
| 定位明确的查找、实现、检查 | 经基线验证的较便宜执行模型 | 只在批准路径内执行，异常/超范围交回主助手 |
| 计数、格式转换、固定规则检查 | 现有程序或工具 | 没有歧义就不调用模型 |

目标模型选择顺序：任务显式 model → 工作流显式执行默认 → 角色执行默认。只有明确要求继承时才使用主模型，不因漏填参数静默回到昂贵主模型。工作流的策略模型与执行默认不能混为一项。

`azure-gateway/gpt-5.6-luna` 是本次已验证可调用的候选，不是已批准全量切换的默认；其他模型需相同任务对照。模型使用精确 provider/model 标识，并记录实际 provider/model、来源与升级原因。候选不可用时明确预检失败，不静默换模型或提高预算。

thinking 随任务难度选择，不继承主助手的高等级作为执行默认。只读/机械任务优先 low，复杂实现可 medium，具体支持等级与质量用基线确认；主助手也不必每轮使用最高等级。

### 9.2 升级与任务身份

一次明确失败、证据不足、设计冲突、超范围或到达软预算时，子助手返回阻碍与已取得证据，由主助手决定调整范围或升级。不能同级无限重试，也不能把全部原始历史交给强模型重做。

现有会话不能直接改 model/thinking，升级创建新执行尝试，传短交接；保留旧尝试、失败与用量，逻辑任务计数仍为一。预算、授权、最终架构和不可逆动作仍由主助手负责。

### 9.3 最小任务包与角色环境

- 独立任务保持 fresh/task_only，零轮父历史；任务包只含目标、允许路径/关键入口、约束、验收与结果格式。现有 1,500-token 上限是任务包边界，不是每次必须填满的目标。
- 不复制父历史、原始日志、文件正文或兄弟完整结果；必要上下文由准确路径、符号与小型摘要提供。
- 只读、代码执行、资料检索分别提供需要的工具/技能/指令，保留项目必要约束、安全护栏、权限检查、trace 与交接能力。不能简单关闭全部扩展来省钱。
- 角色工具限制必须由真实权限/注册机制执行；提示说“不要用”不等于工具已被禁用。未支持精确裁剪时保留安全能力并注明未裁剪，不伪造最小权限。
- 子助手不承接主助手的任务管理、长期记忆、资源授权等职责；只有原任务明确授权且入口支持时才开放相应能力。
- 先定位符号、再读必要范围；批量工具调用返回必要摘要与引用，不原样回传所有读取内容。重复读取需有内容变化、验收或错误修复依据，不能用次数本身判定浪费。

### 9.4 整体预算与结果交接

新增正常任务的成本预算，与现有 MiB 级异常载荷限制分开。预算按角色覆盖启动说明/工具定义、task/context、工作流全部 inputs、执行轮次/输出、时长和累计估算费用；数值由代表任务基线确定，不在本稿承诺未经测量的固定比例。

已有 usage 是事后证据；发送前 token 估算若无对应 tokenizer 就明确为估算，必要时采用字节上限。超过预算时返回明确阻碍，不静默截断关键失败或删安全说明。

交接优先短摘要、最多五条证据、产物路径、风险和未完成项；大产物保存在批准位置。整次工作流 inputs 有总预算，不因每个摘要各自合规就允许累计膨胀。主助手接收必要结论，按代表证据复核而非重读全部材料。

结果格式需验证；当前 compact_result_v1 是软约定，不写成工具已经强制执行。复用现有 outputSchema/结果解析能力，确需补协议时走权威源码与受限桥接，不吞解析错误。

### 9.5 成本记录与准入

按父任务、逻辑任务、执行尝试分别记录模型/思考等级、选择原因、输入/cacheRead/cacheWrite/output、估算来源、交接是否完成、预算与升级状态。字段必须来自实际事件；未知值标未知，不补零伪装。只保留决策相关元数据，不把完整提示、凭证和日志复制进新账本。

净成本 = 主助手策略 + 子助手启动/执行 + 主助手回收/验收 + 失败重做。分别统计首次验收通过率、重做次数、主助手复核 token、完成时长和关键失败。

基线 → 只换执行模型 → 保持模型缩小角色上下文 → 改善读取/交接。每次只变一个主要因素，按同一组任务、相同验收比较；质量与权限门槛不降低且净成本改善后才扩大使用。缓存费用分别计算，reasoning 不重复叠加；没有账单验证时只称估算费用。

## 10. 分阶段实施

### 阶段一：完成项收起与父子导航

候选改动：现有 `WorkbenchPanel`、`LiveSessionPage`、`LiveSessionFeatures`、`LiveSessionsList`，加最小共享投影与针对性测试。具体文件以实施时工作区为准。

先核实实际任务状态集合、两种来源关联、已完成记录和历史读取。完成分组、稳定详情、父子导航及计数。不做自动结束进程。

交付：二十个成功任务不堆积活跃区；成功结果可查；失败、等待批准和未知状态不被隐藏。

### 阶段二：工作流统一层级

复用 `LiveWorkflowProgressCard` 与 `LiveWorkflowPanel` 的总览和阶段能力，工作台采用相同计数和关联规则；工作流内助手不重复出现在普通列表。

先用现有查看/中止能力交付。暂停与重试只有桥接验证通过后加入，不阻塞基本分层展示。

交付：一个二十任务工作流只有一个顶层入口；可定位失败任务、查看结果，旧尝试不会覆盖新尝试。

### 阶段三：执行模型选择与质量基线

在运行器权威源码增加第 9.1 节的显式/角色默认选择与选择原因记录，工作流任务使用执行默认。先用同一组任务只改变执行模型，保持提示、工具和验收不变；升级创建新尝试。

交付：遗漏 model 不静默继承强主模型；显式覆盖有效、实际模型可查；质量门槛不降低，净成本/重做有可复核记录。候选模型未过基线前不宣称全量切换安全。

### 阶段四：上下文、交接与预算

按角色缩小启动包，优先复用现有权限与工具注册，保留安全/trace；增加整次输入和结果预算、有界读取、结构化交接、依赖推进与重复通知收敛。每项主要因素单独实验，不与阶段三同时大改。

交付：启动和交接实际用量下降；无必要的全文回传减少；权限检查仍有效；预算耗尽明确汇报；相同结果不重复取回或触发分析。已到达的延迟提醒与已取消的检查也能安全消费。

### 阶段五：运行器收尾

基于已完成静态检查，再运行验证结果保存、后台命令归属、交接、恢复和通知去重。能复用则不新增协议；确需新增时采用明确、兼容的字段与能力声明。

交付：结果交接与执行退出有独立证据；追问/清理竞争不丢消息；重复通知不重复推进主会话。

缺少运行器修改权限时，将相关阶段标为未实施；展示工作继续交付，不伪造模型已切换、token 已减少或资源已清理。

## 11. 验收与最小验证

| 场景 | 必须观察到的证据 |
| --- | --- |
| 连续完成 20 个普通子任务 | 活跃区无 20 张完成卡片；已完成分组有全部结果入口 |
| 成功时详情正在打开 | 详情和选中任务不跳变；进程退出后仍有记录或明确不可用原因 |
| 成功记录断开 | 不从任务历史消失；不把连接断开当成功或退出证明 |
| 失败、等待批准、未知状态 | 明确标识并保留可见入口；失败与成功计数分开 |
| 1 个工作流、20 个任务 | 一个顶层入口；阶段层级可展开；内部助手无重复顶层项 |
| 相同完成事件重复到达、重连 | 完成记录和主助手通知不重复；新快照覆盖过期状态 |
| 任务重试、后续追问 | 尝试记录分别保留，逻辑任务不重复计数；消息得到明确接收或拒绝 |
| 父会话不可见、多 slot | 未关联助手可访问，不混入其他会话、不泄漏结果 |
| 后台命令未结束 | 无误杀、无丢失命令通知；释放状态与实际归属一致 |
| 资源释放 | 运行器/进程退出证据与结果交接证据各自可查 |
| 模型遗漏/显式覆盖/工作流默认 | 普通执行采用角色默认；显式覆盖有效；实际模型与选择来源可查，不暗中继承强主模型 |
| 验收失败后的升级 | 新执行尝试使用明确模型和短交接；旧尝试/费用保留，逻辑任务只计一次 |
| 角色工具与系统说明 | 实际启动包可量化缩小；任务必需能力和安全护栏仍有效，未授权协调/记忆能力不可调用 |
| 多输入交接/预算耗尽 | 整体预算有效；明确返回阻碍；关键失败/证据不被静默截断 |
| 成功通知、定时检查延迟送达 | 已处理结果不重复收集或续跑；无残留重复检查，依赖满足时仍能继续任务 |
| 成本对照 | 同题同验收、一次一项改动；质量不下降，统计主助手复核/重做后的净成本而非只看子助手单价 |
| 宽屏、窄屏、200% 缩放、明暗主题 | 状态可读、键盘可操作、无意外整页横向滚动 |

每阶段只运行相关状态投影、页面、模型解析与命令验证测试；模型/成本阶段补同题质量与净成本对照，资源阶段补执行集成检查。浏览器视觉、模型质量与运行器实测未完成时分别说明，不用单元测试代替，不先承诺节省百分比。

## 12. 风险、兼容与上线边界

- 旧快照字段不足：保持可见并说明待确认，不猜终态。
- 归档后无法查结果：阶段一先确认保留路径；不能靠隐藏连接换取假清理。
- 自动收尾误停执行：仅运行器拥有释放权限，检查工具与后台命令，不按 idle 自动退出。
- 页面控制能力与工具不一致：按真实接口能力显示，不先放假按钮。
- 便宜模型重做更多：按净成本和首次验收准入，不只比单价；保留明确升级，不无声提高预算。
- 裁剪上下文丢失项目约束或安全：安全/权限检查必过；只去掉执行角色不需要的内容，不全局关闭扩展。
- 已有任务依赖模型继承：默认选择改动单独评审，提供明确继承/覆盖路径并保留尝试版本；不修改已运行会话模型。
- token/费用来源不一致：按 provider usage 与计价来源分列，缓存/推理不重复计数，不拿字符数替代账单。
- 当前仓库已有大量无关未提交改动：实施只做必要差异，不覆盖其他工作。

第一阶段纯展示改动不要求改变安装、版本或环境变量。本次方案不是部署指南。后续若影响配置、组件关系、依赖或环境变量，必须同步 `guide/`；修改后端环境变量读取时运行 `npm run docs:env-check`。

部署、构建与服务重启由用户执行 `pi-dashboard/run.sh` 或自己的启动方式；Agent 不执行、不停止运行中的 Dashboard。回退只针对本次改动，不回退无关工作。
