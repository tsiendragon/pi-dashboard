# 服务面板（`/services`）

一屏看清本机上各个服务「有没有在应答」：状态灯、HTTP 码、延迟、页面链接，以及能直接点的启动 / 停止 / 重启。

**先说清能力边界**：这个页面只能操作**运行 dashboard 的那台机器**上的进程。别的机器上的服务（例如服务主机上的 DataHub / ModelCenter / CardLib）只能显示探测结果和链接，不能启停——跨机执行需要额外的远程执行器，当前没有做。

---

## 1. 服务清单是数据，不是代码

所有登记都在 `~/.pi/services.json`。文件不存在时，第一次打开页面会按内置默认写一份，之后随便改，刷新页面生效（不需要重启 dashboard）。

```json
{
  "version": 1,
  "services": [
    {
      "id": "presentation-center",
      "label": "Presentation Center",
      "group": "本机",
      "cwd": "/path/to/presentation-center",
      "start": ["bash", "scripts/start.sh"],
      "stop": ["bash", "scripts/stop.sh"],
      "probe": { "url": "http://127.0.0.1:8765/health" },
      "webui": "http://127.0.0.1:8765/"
    }
  ]
}
```

| 字段 | 必填 | 作用 |
|---|---|---|
| `id` | 是 | 唯一标识，`[a-z0-9-]`；地址里用它（`/api/services/<id>/start`） |
| `label` | 是 | 页面上显示的名字 |
| `group` | 否 | 页面上的分组标题，默认「未分组」 |
| `managed` | 否 | `false` = 只读行：显示状态和链接，不给按钮。远端服务、dashboard 自己都用它 |
| `note` | 否 | 卡片上的一句说明 |
| `cwd` | 否 | 执行命令的工作目录；不存在时拒绝执行并报错 |
| `start` | 否 | 启动命令，**argv 数组**（不经 shell） |
| `stop` | 否 | 停止命令，argv 数组；优先于端口兜底 |
| `env` | 否 | 只对该服务追加的环境变量（例如 `PORT`） |
| `stopPort` | 否 | 停止时按这个端口找监听进程；不写则从 `probe.url` 推 |
| `startTimeoutMs` | 否 | 启动后等多久算失败，默认 15000。冷启动慢的服务（Python 从共享存储 import）要调大，比如 60000 |
| `probe` | 否 | 健康探测：`url` + 可选 `okStatus`（默认 2xx/3xx 算健康）、`timeoutMs`（默认 4000） |
| `webui` | 否 | 页面地址（通常是 `127.0.0.1`） |
| `webuiPublic` | 否 | 浏览器能直接打开的地址（网关/域名）；填了优先用它 |
| `log` | 否 | 日志文件；不写则用 `~/.pi/logs/services/<id>.log` |

没有 `probe` 的条目状态显示「不可探测」（例如纯命令行工具）。

---

## 2. 状态怎么来的

每 4 秒（页面可见时）请求一次 `GET /api/services`，后端对每条 `probe.url` 发一次 HTTP 请求，只取状态码，不读响应体。

| 显示 | 含义 |
|---|---|
| 在线（绿） | 状态码在 `okStatus` 内（默认 2xx/3xx） |
| 离线（红） | 请求失败或状态码不符，卡片上给出原因 |
| 不可探测（灰） | 没配 `probe`，或该行是只读条目且没有探测地址 |

**为什么不用进程存活判断**：很多服务的父进程、启动方式各不相同（前台 uvicorn、tmux、nohup），用「接口答不答话」才是用户真正关心的结果。

---

## 3. 启动 / 停止 / 重启怎么执行

- **启动**：`spawn(command, args, { detached: true, stdio: [ignore, log, log] })` + `unref()`。子进程脱离 dashboard，dashboard 自己重启不会把它带走。启动后最多等 10 秒看探测是否转绿，结果直接回给页面。
- **停止**：先跑 `stop` 命令；如果没有 `stop` 命令，或跑完端口还被占着，就按端口找到监听进程发 `SIGTERM`，等不到退出再发 `SIGKILL`。找进程用 `/proc/net/tcp` + `/proc/<pid>/fd`，不依赖 `lsof`。
- **重启** = 停止 + 等待 + 启动。
- **日志**：点卡片上的「日志」看登记日志文件的结尾 200 行（最多 400 行）。

命令以 argv 数组保存、**不经过 shell**，所以不需要转义；管道和重定向请写进脚本，登记脚本路径。

---

## 4. dashboard 自己那一行是只读的

`pi-dashboard` 条目故意是 `managed: false`：页面点「重启」等于自己把自己杀掉，页面会立刻断线；如果 dashboard 是前台 `./run.sh` 起的，还会连带结束当前所有 live session。

要重启 dashboard，请回终端：

```bash
cd /path/to/pi-dashboard && ./run.sh
```

如果以后把 dashboard 交给 systemd 托管，可以再单独加一条「延迟重启」的登记项，不要直接在这里点。

---

## 5. 链接为什么能直接点开

登记里写的是 `127.0.0.1:8765` 这类本机地址，浏览器多半在另一台机器上，直接点会打不开。所以页面会做一次推导：

- 当前页面若是通过平台网关打开的（host 形如 `<实例>-proxy-7777.<网关域名>`），就把端口换成该服务的端口，得到同网关的兄弟地址，例如 `<实例>-proxy-8765.<网关域名>`。
- 推导不出来时，用的就是登记的原地址，鼠标悬停会提示「只有本机能打开」。

想固定某个地址就填 `webuiPublic`，它永远优先。

> 注意：被探测的服务必须监听 `0.0.0.0` 才能从网关访问。只监听 `127.0.0.1` 的服务（默认配置下的 XDoc Monitor 就是这样）只能在本机或自建 SSH 隧道里打开——不要为了能点开就把无鉴权的服务改成 `0.0.0.0`。

## 6. 安全边界（重要）

这个页面等于给 dashboard 增加了「执行命令」的能力，所以：

- 命令**只能**来自 `~/.pi/services.json`，请求体里只有 `id`，不接受任何前端传入的命令串。
- 启动 / 停止 / 重启三个写接口走 `requireBrowserAuth`：需要一次 Live Pi 浏览器认证（cookie），否则返回 401；来源不被允许返回 403。这和终端、live session 用同一套凭证。
- 读接口（清单、日志）不额外认证，沿用 dashboard 的既有前提：**只在内网/本机可达，不要直接暴露到公网**（见 [remote-access-deployment.md](remote-access-deployment.md)）。
- 清单文件是普通用户可写文件：能改它的人本来就能在这台机器上执行命令，这不是额外的提权面。

**注意没有登录验证的服务**：有些自带 WebUI 的服务自己不做认证，典型是 `sekret local ui`（Sekret 凭证库）。它把页面开在 `0.0.0.0`，而且能列出、解锁、增删凭证——只要能访问那个端口的人就能操作。这类服务只应该在可信内网开，用完在页面上点「停止」。不要把它注册成随机器常开。

> `sekret local ui` 的监听地址写死为 `0.0.0.0`，命令行参数只能改端口。如果哪天需要收紧，得在它自己仓库里改，或者在网络层限制访问——不要靠改这里的 `probe.url` 来“藏起来”。

## 7. 排障

| 现象 | 处理 |
|---|---|
| 页面提示「认证」 | 到 Live Pi 页面粘贴一次访问令牌，拿到 cookie 后重试 |
| 点启动后报「秒内没有应答」，但进程其实活着 | 服务启动比等待窗口慢。把该条目的 `startTimeoutMs` 调大（毫秒），例如 `60000` |
| 点启动后报「秒内没有应答」，日志也没有新内容 | 命令本身没跑起来：检查 `start` 路径、`cwd`、环境变量 |
| 清单读取失败 | JSON 语法错或字段不合法，页面会显示具体原因；修好文件刷新即可 |
| 某个服务状态一直是「不可探测」 | 它没配 `probe`，或探测地址写错 |
| 停止成功但端口还在 | 该进程可能被其他父进程拉起，检查 `stop` 命令是否完整 |
